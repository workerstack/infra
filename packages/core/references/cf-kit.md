# Worker configs from one env

A product writes one `infra.config.ts`. The value `defineInfraConfig` returns is the config and the kit at once. Each Worker's `cloudflare.config.ts` imports it and asks it for bindings, vars and secrets per scope (`local`, `dev` and `prod`), so every Worker reads the same env.

```ts
// apps/web/infra.config.ts
import { defineInfraConfig } from "@workerstack/infra";

export default defineInfraConfig({
  cloudflare: {
    bindings: { local: { d1_databases: { DB: { database_id: "db-local-id", database_name: "db-local" } } } },
    zone: { domain: "example.com", zoneId: "0123456789abcdef0123456789abcdef" },
  },
  env: { dev: {}, global: {}, local: { GREETING: "hi" }, prod: {}, sealedKeys: () => new Set(["API_KEY"]) },
});
```

A Worker's `cloudflare.config.ts` is then one call:

```text
// apps/web/api/cloudflare.config.ts
import infra from "../infra.config.ts";

export default infra.worker("api", {
  compatibilityDate: "2026-01-20",
  d1: ["DB"],
  entrypoint: "./src/index.worker.ts",
  routes: ["example.com/api/*"],
  secrets: (env) => [env.API_KEY],
  vars: (env) => [env.GREETING],
});
```

`infra.worker(base, options)` (`options` may be `(scope) => options`, called per scope, so a prod-only route or binding stays in the short form) returns what `defineConfig` of `cf/config` takes, so the file default-exports it with no wrapper (`defineConfig(infra.worker(...))` works too). Per `--mode` it builds `...infra.defaults`, the scoped name (`api-dev`), each binding kind from its names and the routes, then merges `extra(scope)`:

- `d1`, `kv`, `r2`, `queue`, `aiSearch`, `analytics`, `secrets`, `vars` and `ratelimits` take what the kit's method of that name takes; `services` maps a binding to a target Worker's base name. `vars` unset means no vars, not even `ENVIRONMENT`.
- `routes` land on the config's zone; `zone` overrides it. Routes with no zone fail naming the Worker.
- `entrypoint` names the Worker module. Name it `*.worker.ts`: @workerstack/repo treats that file and every `*.config.ts` as loaded by a tool, so knip needs no ignore and the default export needs no lint skip.
- `minify`, `uploadSourceMaps` and `assetsDirectory` are the build settings `infra gen` writes to Wrangler as `minify`, `upload_source_maps` and `assets.directory` (resolved against the package). `minify` is `true` for every Worker unless it is set to `false`. They ride on the returned function, not in the Cloudflare config, so a package whose `infra.worker` sets one and that also has a `wrangler.config.ts` fails gen naming both files.
- `extra(scope)` is merged last, for anything the shorthand does not cover: its `env` beside the shorthand's bindings, its `triggers` after the routes, any other key over the rest.

The long form still works, for what `extra` cannot say (a container, say): the same methods by hand. A long-form package keeps its build settings in `wrangler.config.ts` (`defineWranglerConfig({ minify: false })`, `minify` still defaulting to `true`), because Cloudflare's `WorkerConfig` has no `minify` key to carry them.

```text
export default defineConfig(({ mode }) => {
  const scope = infra.scope(mode);

  return {
    worker: {
      ...infra.defaults,
      env: {
        ...infra.d1(scope, "DB"),
        ...infra.secrets((env) => [env.API_KEY]),
        ...infra.vars(scope, (env) => [env.GREETING]),
      },
      entrypoint: "./src/index.worker.ts",
      name: infra.name("api", scope),
    },
  };
});
```

`infra.scope(mode)` is the scope of a `--mode` (Vite's `development` is `local`); `infra.env.local` and the other views still read the env. Binding names type-check against the config's bindings, and var and secret names against the env's keys: `infra.d1(scope, "NOPE")` and `infra.worker("api", { d1: ["NOPE"], entrypoint })` are type errors. The kit's options live in `cloudflare.workers` (see Config): `defaults`, `migrations`, `localRemote` and `ratelimitIds`.

## Migrations

`migrations` names, per D1 binding, the directory of its migrations, the Worker that owns them and, optionally, the database its `database.migrate.config.ts` calls it:

```text
// infra.config.ts, in cloudflare.workers
migrations: { DB: { database: "main", dir: join(import.meta.dirname, "db/migrations"), owner: "web-api" } },
```

- `dir` and `owner`: `infra gen` writes `migrations_dir` into the owner Worker's config. Nothing else of `migrations` lands in the generated files.
- `database`: `infra gen` writes `database.migrate.config.ts` beside `dir`, headed `// @generated by @workerstack/infra`: the database by that name, its `migrationsDir`, and per deploy scope (`dev`, `prod`) the owner Worker's `.cloudflare/wrangler.<scope>.json`, where wrangler finds the database by its binding. `--check` fails a stale one like a wrangler file; a hand-written one without the header fails both, naming it: delete it and gen writes it. `infra db-migrate` runs `database migrate apply main -e <scope> --yes --json` for the binding, in the nearest directory from `dir` up to the product root that holds `database.migrate.config.ts`. A binding with no `database` is skipped.
- `infra db-wipe` reads the tables the `.sql` files in `dir` create, so it empties those and drops the rest.

## Rate limits

`infra.ratelimits(worker, scope, ...limits)` gives each limiter its namespace id from the registry. `infra gen` gives a new limiter the next free id and writes it there. The registry is `cloudflare.workers.ratelimitIds` when set, else `ratelimit-ids.json` at the product root: the root `infra` loaded the config from, or, in a process `infra` did not start (`cf workers types`, `vite dev`), the nearest directory above the working directory that holds an `infra.config.ts`. Commit the file, so an id never changes.

## The product

- The kit is `infra.config.ts`'s default export (`isCfKit` tells). A default export that is not `defineInfraConfig`'s value fails the command.
- A Worker package is a directory with a `cloudflare.config.ts`. node_modules, .git and .worktrees are skipped.
- A kit file left from before fails `infra gen`, naming its move:

```console
infra gen: apps/web: web.cf-kit.ts: the kit is built by defineInfraConfig now; move its options to cloudflare.workers in infra.config.ts and delete the file
```

## Sealed and plain

Keys are picked by property, never by string: `vars: (env) => [env.GREETING]`, `secrets: (env) => [env.API_KEY]`, `infra.vars(scope, (env) => [...])` and `infra.secrets((env) => [...])`. A property gives rename, find-references and go-to-definition, and the vars map holds no sealed key while the secrets map holds only sealed keys, so a wrong pick is an editor error.

- `infra.vars(scope, pick)` takes plain values. A sealed key never lands in a var.
- `infra.secrets(pick)` takes sealed values. A key must be sealed in `local`, `dev` and `prod`, because a secret goes up with a deploy and runs locally from `.dev.vars.local`. With no `sealedKeys` on the env, nothing is sealed, so a product with secrets gives it.
- A secret with no value in a scope fails naming the key and scope.

The two errors, each printed as `infra gen: <product>: <message>`:

```console
infra gen: apps/web: API_KEY is sealed in local; ask kit.secrets for it, not kit.vars
infra gen: apps/web: GREETING is not sealed in prod; a secret must be sealed: bun repo env set GREETING --scope prod
```

## Generating

```console
$ infra gen
wrote apps/web/api/.cloudflare/wrangler.local.json
wrote apps/web/api/.dev.vars.local
$ infra gen --check
infra gen: apps/web: apps/web/api/.cloudflare/wrangler.dev.json is out of date; run infra gen
```

`infra gen [name|--all] [--check]` writes `.cloudflare/wrangler.<scope>.json` and `.dev.vars.<scope>` for every Worker package, then types each with `cf workers types`. `--check` writes nothing and exits 1 naming each file that is out of date.
